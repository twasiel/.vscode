# VS Code setup for competitive programming (C++)

A minimal VS Code configuration for writing, building, running and debugging single-file C++ solutions. Open any `.cpp` file and build, run or debug it with one shortcut. No CMake or Makefile is needed.

## Requirements

> [!IMPORTANT]
> **KDE Konsole is required for debugging.** The debug configuration starts the program in an external `konsole` window, so you can type into stdin while stepping through the code. Without Konsole installed, the debugger will not launch.

| Tool | Used for |
| --- | --- |
| [KDE Konsole](https://konsole.kde.org/) | External terminal for the debugged program |
| `g++` with C++20 support | Building (`build` task) |
| `gdb` | Debugging |
| libasan / libubsan | AddressSanitizer and UndefinedBehaviorSanitizer (usually shipped with GCC) |

### Recommended extensions

VS Code offers to install these when you open the folder (see `extensions.json`):

- [clangd](https://marketplace.visualstudio.com/items?itemName=llvm-vs-code-extensions.vscode-clangd) (`llvm-vs-code-extensions.vscode-clangd`): code completion, diagnostics, go to definition
- [Native Debug](https://marketplace.visualstudio.com/items?itemName=webfreak.debug) (`webfreak.debug`): provides the `gdb` debug type used in `launch.json`
- [C/C++](https://marketplace.visualstudio.com/items?itemName=ms-vscode.cpptools) (`ms-vscode.cpptools`): the `cppbuild` task type and the `$gcc` problem matcher

> [!TIP]
> clangd and the IntelliSense in C/C++ conflict with each other. If you use clangd, set `"C_Cpp.intelliSenseEngine": "disabled"` in your settings.

## Files

| File | Purpose |
| --- | --- |
| `extensions.json` | Recommended extensions |
| `tasks.json` | Build and run tasks |
| `launch.json` | gdb debug configuration |

## Usage

### Build

The **`build`** task compiles the file currently open in the editor:

```sh
g++ -std=c++20 -O2 -Wall -Wextra -fsanitize=address,undefined -g <file>.cpp -o <file>
```

- `-std=c++20`: modern C++
- `-O2`: the optimization level most judges use
- `-Wall -Wextra`: catch common mistakes at compile time
- `-fsanitize=address,undefined`: catch out-of-bounds access, use-after-free, signed overflow and similar bugs at runtime
- `-g`: debug symbols

The binary is placed next to the source file, with the same name and no extension.

Run it from **Terminal → Run Task… → build**.

### Run

The **`run`** task builds the current file and then runs it in a dedicated, cleared terminal panel. It is the default test task, so you can bind it to a key via `workbench.action.tasks.test`, or run it from **Terminal → Run Task… → run**.

### Debug

Press **F5** with a `.cpp` file open. The debug configuration:

1. Runs the `build` task first.
2. Starts the binary under `gdb` in a new **Konsole** window, where you enter the input.
3. Uses GDB pretty printers, so STL containers such as `vector` and `map` show up readably in the Variables panel.

### Default build task (Ctrl+Shift+B)

**Ctrl+Shift+B** runs `C/C++: gcc build active file`, a plain debug build with no warnings, sanitizers or optimizations. It was generated by the C/C++ extension. For the full flag set, use the `build` task instead.

## Portability notes

The compiler paths point to `/run/current-system/sw/bin/`, which is where [NixOS](https://nixos.org/) puts system packages. On other distributions, change them in `tasks.json` to `g++` / `gcc` (or `/usr/bin/g++` / `/usr/bin/gcc`).

To use a terminal other than Konsole, change `"terminal": "konsole"` in `launch.json`.
